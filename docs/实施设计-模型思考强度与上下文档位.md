# 实施设计：模型思考强度与上下文档位（Web 对话）

- 状态：设计已确认（4 项决策已定，见 §10）；P1 已落码，压缩改为产品侧守卫实现（§7 已改口，不改框架包）
- 范围：`luban-agent`（Web 对话页 + 配置/会话存储 + 上下文压缩守卫）；**不改 `luban-framework`**
- 上游设计依据：**无**。本文件是该需求的首份需求与实施设计，此前仓库内无相关 PRD。

---

## 1. 目标与非目标

### 1.1 目标

1. Web 对话页可按**当前模型**给出思考强度选项：模型不支持思考则不显示；模型只支持 2 档就只出现 2 项。
2. Web 对话页可按模型给出**上下文档位**（`300K / 600K / 900K / 1M` 这类），并在选中档位后**真实驱动会话压缩**，而不是只做个开关。
3. 思考强度与上下文档位支持**全局默认 + 会话覆盖**，与现有「全局默认模型 + 会话级模型」的选择模型一致。
4. 未登记的模型不猜测：默认只提供「跟随模型」，由用户在设置中心登记能力后启用。

### 1.2 非目标

- 不支持非标思考参数（`enable_thinking`、`thinking.budget_tokens`、`thinking.type`、`output_config.effort` 等）。本轮只走 `reasoning_effort` 的标准枚举子集。
- 不做模型能力的自动探测（不调厂商 models 端点推断档位）。
- 不改 CLI / Codex 的思考强度交互（不新增档位控件，继续跟随模型）；上下文压缩标记三端同步显示（§7.4）。
- 不引入 token 精确计数（分词器）。仍用字符估算，见 §7.3。

### 3.2 由核查得出的三条硬结论

1. **厂商档位 ≠ 我们的枚举**。厂商普遍用 `xhigh` / `max` 作为最高档，而 `Microsoft.Extensions.AI` 只有 `None/Low/Medium/High/ExtraHigh` 五个值。映射已核实：`ExtraHigh` → `"xhigh"` 是通的；`minimal` 与 `max` 在本轮**发不出去**（详见 §3.4）。
2. **思考开关不统一，而且常常不在 `reasoning_effort` 里**。GLM-5.3 / Kimi K3 / MiniMax M3.1 明确**不允许关闭思考**；豆包 `doubao-seed-evolving` 与 GLM-5.2 的档位表里有 `none`/`minimal`（可停思考），但豆包「关思考」的官方推荐仍是 `thinking.type=disabled`（非标字段）；DeepSeek 关思考同样要 `thinking.type`。因此 `None` 这一项必须**按模型声明**，不能全局提供。
3. **没有厂商把"上下文长度"当请求参数**。绝大多数窗口是固定的，个别模型（qwen3.8-max）因思考模式不同，输入上限有几十 K 的差异。所以「上下文档位」只可能是**我们客户端的行为**（提前压缩），不可能是发给模型的参数——这一点在 §7 落地，UI 文案也必须照此表述。

### 3.4 标准链路能发出的值域（已核实）

`Microsoft.Extensions.AI.OpenAI` 11.0.0 的私有方法 `OpenAIChatClient.ToOpenAIChatReasoningEffortLevel` 是 `ReasoningEffort` 进 `reasoning_effort` 的唯一出口，其分支为：

```csharp
ReasoningEffort.None      => ChatReasoningEffortLevel.None,
ReasoningEffort.Low       => ChatReasoningEffortLevel.Low,
ReasoningEffort.Medium    => ChatReasoningEffortLevel.Medium,
ReasoningEffort.High      => ChatReasoningEffortLevel.High,
ReasoningEffort.ExtraHigh => new ChatReasoningEffortLevel("xhigh"),
_                         => null
```

校验方式：包内 `lib/**/Microsoft.Extensions.AI.OpenAI.dll` 的 UTF-16 字面量表里 `xhigh` 出现 1 次、`minimal` 出现 0 次；`OpenAI.dll` 2.14.0 的 `ResponseReasoningOptions` 值表里同时存在 `minimal`、`xhigh`、`max`。即：

| 我们可发的值 | 落到线上的 `reasoning_effort` |
|---|---|
| `None` | `none` |
| `Low` | `low` |
| `Medium` | `medium` |
| `High` | `high` |
| `ExtraHigh` | `xhigh` |
| （无对应值） | `minimal`、`max` **均不可发** |

1. 内置表只放「官方文档写明、且能映射到 §3.4 可发集合」的组合；`max` / `minimal` 一律不收（发不出去）。

## 4. 设计总览

### 4.1 三层数据

```
模型能力档案（是什么）              用户选择（要什么）          生效路径（做什么）
ModelProfiles[provider:model]  →  全局默认 / 会话覆盖  →  ① 每轮 ReasoningEffort
  内置表[模型 id]（兜底）                                   ② 压缩触发阈值 = min(档位, 窗口 − 留白)
  Reasoning: string[]?
  ContextWindow: int?
```

### 4.2 语义定义（关键，写死在文档里避免歧义）

| 字段 | `null` / 缺省 | 空数组 `[]` | 非空 |
|---|---|---|---|
| `Reasoning` | **未知**：UI 只给「跟随模型」 | **标准链路无档位**：不显示该控件（真·非推理模型，或官方明确不支持 `reasoning_effort`，或只能用非标字段开关） | 该模型可选的枚举名子集 |
| `ContextWindow` | **未知**：不显示控件；压缩跳过预检，仅靠超长兜底（§7.3） | 同左（不允许 `0`） | 模型真实窗口 token 数 |

### 4.3 上下文档位派生规则（不落盘，纯计算）

依据用户规则：**低于 300K 的用模型最大长度；达到 300K 的按 300K 倍数分档，默认取窗口本身（末档）。**

```text
if (window == null)          tiers = []            // 未知
else if (window < 300_000)   tiers = [window]      // 固定，UI 只读展示
else {
    tiers = [300k, 600k, 900k, ...]                // k * 300k <= window
    if (window > tiers.Last()) tiers.Add(window)   // 末档取实际窗口
}
defaultTier = tiers.LastOrDefault()                // 窗口本身：默认不提前压
threshold   = min(选中档位, window - max(window*15%, 16k))   // → min(档位, 窗口 − 留白)
```

| 窗口 | 档位 | 默认 | 默认实际触发点 |
|---|---|---|---|
| 128K | `[128K]`（固定） | 128K | ≈109K（留白 19.2K） |
| 300K | `[300K]`（等效固定） | 300K | 255K（留白 45K） |
| 400K | `[300K, 400K]` | 400K | ≈340K（留白 60K） |
| 600K | `[300K, 600K]` | 600K | ≈510K（留白 90K） |
| 1M（1,048,576） | `[300K, 600K, 900K, 1M]` | 1M | ≈891K（留白 15%） |

> 派生只依赖 `ContextWindow` 一个数，规则改了不需要迁移任何已存数据。

档位的含义是「用户愿意在多大的上下文上花成本」：选更小的档位表示**宁可早点压**，不会被窗口抬高；选末档也不等于贴着窗口跑，实际触发点还要留出窗口余量（留白规则见 §7.5）。

### 5.3 解析服务（core scoped）

新增 `ISessionGenerationSettings`（`LubanAgentCore/Configuration/`）：

```csharp
public interface ISessionGenerationSettings
{
    /// <summary>解析本轮思考强度：档案未知即 null，否则会话列 → 全局默认 → null（跟随模型）。</summary>
    ValueTask<string?> ResolveReasoningEffortAsync(string? sessionId, CancellationToken ct = default);

    /// <summary>解析上下文预算（token）：会话列 → 全局默认 → 档位默认 → 未知返回 null。</summary>
    ValueTask<int?> ResolveContextBudgetAsync(string? sessionId, CancellationToken ct = default);

    /// <summary>按 §4.3 生成档位清单；窗口未知返回空。</summary>
    IReadOnlyList<int> GetTiers(string modelKey);
}
```

注册位置：`LubanAgentCore/Hosting/AgentHostBuilder.cs`，紧随 `IAgentModelSelection`（现有 scoped 注册处）。

`ResolveReasoningEffortAsync` 的解析链（顺序有硬约束）：

```text
档案 Reasoning 未知（null）或为空集合 → null（不发该字段，跟随模型）
否则 session.ReasoningEffort 有值且在该集合内 → 用它
否则 config.Defaults.ReasoningEffort 有值且在该集合内 → 用它
否则 → null
```

「档案未知就不发」优先于全局默认：不知道对方收不收 `reasoning_effort` 时宁可不发，避免把请求打成 400。

`ResolveContextBudgetAsync` 的解析链（两个来源都先按当前窗口收敛，换模型后残留的大档位不会超窗）：

```text
window = 当前模型档案的 ContextWindow
window 未知 → null（跳过预算预检，仅靠超长兜底；框架按条数的自动压缩仍在）
否则 tier = session.ContextTier 是合法档位 → 用它
            否则 config.Defaults.ContextTier 是合法档位 → 用它
                  否则 → 档位默认（末档 = 窗口本身）
     返回 min(tier, window - max(window*15%, 16k))
```

## 7. 压缩预算落地（产品侧守卫，不改框架包）

> 本节初稿按「框架新增 `ISessionCompactionPolicy` 接缝」设计，实施时改为**产品侧装饰 `IAgentHost`**：零框架改动、无需发包。7.1 保留原分析，作为不选该方案的依据。

### 7.1 为什么不选框架接缝

`SessionChatHistoryProvider.cs:112` 的判定是 `history.Count > _targetCount + _threshold`，`_targetCount` / `_threshold` 来自 `LuBanAgentOptions.Session`（`LuBanAgentOptions.cs:169`），装配在 `LuBanAgentFactory.BuildHistoryProvider`（`LuBanAgentFactory.cs:250`）。它**只看条数**，无法表达「1M 窗口」与「128K 窗口」的差别。

`IAgentSessionExtension`（`IAgentSessionExtension.cs`）只在**建 Agent 前**、会话 scope 上调用一次（`AgentHost.cs:448` 附近），拿不到每轮 history 的装配点。要在 history 装配点按预算介入，只能改框架并重新发包。

替代路径：`IAgentHost.RunStreamingAsync` 是三端共用的回合入口，产品侧装饰它即可在**发请求前**按预算压缩，同时捕获「首调仍超长」的失败。CLI / Codex / Web 本地模式共用 `AgentHostBuilder`；远程模式（`AgentClientConnection` 走 `HttpAgentHost`）的实际回合在被连的宿主进程里跑，压缩只发生一次。框架侧既有按条数的自动压缩保持原样（Web 宿主配 `CompactTargetMessages=200` / `CompactThreshold=20`，超过 220 条触发；CLI / Codex 沿用默认 20 / 10），两者互不覆盖。

### 7.3 触发条件与保留窗口

**起跑前预检**：`threshold = await ISessionGenerationSettings.ResolveContextBudgetAsync(sessionId)`（已按窗口留白收敛，见 §7.5），`tokens = Σ 活跃消息估算 + 本轮输入估算`；`tokens > threshold` 时先压缩再发请求。阈值为 `null`（模型窗口未登记）时跳过预检。

**超长兜底**：首调以「上下文超长」结束、且本轮**零产出**（无正文/思考/工具事件）时，压缩后重跑一次；重跑仍超长则把原始错误交回调用方。超长判定两路——流内 `ErrorEvent` 文案命中「上下文超出模型长度上限」/ `context_length_exceeded` / `maximum context length` / `too many tokens`，或流内抛出 `AgentApiException` 且 `Error.Category == ContextLengthExceeded`（沿内层异常链向下找 3 层）。已有产出时不重跑，避免「半成品 + 完整正文」两份输出。

**保留窗口**按 token 从尾部累加，上限 = `min(CompactionOptions.KeepTokens, 阈值的一半)`（默认 15k；那一半是给系统提示、工具定义与模型回复留的余量），**不再看消息条数**——条数与真实长度无关，长会话会被「1000 条」撑爆、短会话又留不够。阈值为 `null` 时上限回落为「压缩前估算的一半」，保证仍然实际减半。会话不止一条时**至少保留最新一条**：没有接续点，下一轮只能对着一堆摘要说「继续」；只有一条时不存在接续问题，硬留等于不压缩，仍按上限判断。

**摘要输入上界**：摘要调用同样受会话模型窗口约束，喂**全部归档消息**（复用同一段历史的 prompt cache），上限 = 阈值 × `SummarizePercent`（默认 80%）；超出时从最老的开始丢，单条正文按上限一半字符截断。阈值为 `null` 时取 `min(压缩前一半, 4000)`。否则摘要调用自己就超窗，兜底永远救不回来。

**落库顺序**：先写 `role=summary` 摘要，再标记被摘要消息 `is_compacted=1`；反序执行时若归档成功而写摘要失败，历史会被永久裁掉。框架重建历史时把最新摘要作为 `[对话摘要]` 系统消息喂给模型（`SessionChatHistoryProvider.ProvideChatHistoryAsync` 末段）。摘要器未真正归约（例如归档窗口里含 `system` 消息，会被单独前置保留）时整轮放弃、不写库——宁可这轮不压，也不能拿一条正文冒充摘要。

**TOKEN 估算**：中日韩字符按 1 字 1 token，其余字符按 4 字符 1 token。**只计正文与附件占位**——思考、工具调用与段落存库供展示和排查，不回放、不占上下文，因此不计入。相比框架的 `text.Length / 4`，中文口径更保守（真实分词通常 ≤ 1 token/字），英文/代码仍可能低估。

### 7.4 三端压缩标记

压缩事件名为 `AgentSseEventNames.ContextCompacted`（`context.compacted`）。框架 `AgentEventProtocol.ToFrame` 不认识产品侧事件类型（返回 null），因此各端都要显式接：

| 端 | 落点 |
|---|---|
| Web 实时流 | `WebAgentService.StreamFramesAsync` 在 `ToFrame` 前特判转帧；`web/src/stores/chat.ts` 的 `context.compacted` 分支渲染提示 |
| Web 重连快照 | `AgentRunHandle.Accumulate` 把该帧写入 `_notices`，快照按序回放 |
| CLI | `ConversationViewModel` 的 `ContextCompactedEvent` 分支；历史 `role=summary` 显示压缩标记 |
| Codex | `SessionViewModel` 流式分支；`MainWindowViewModel` 历史 `case "summary"` |
| 远程客户端 | `AgentEventTranslator.TryTranslate` 还原事件，`HttpAgentHost` 按普通事件透传 |

压缩失败发 `phase=failed`（「⚠️ 上下文压缩未生效，历史保持原样」），避免 UI 停在「正在压缩…」。

### 7.5 触发阈值（档位封顶 + 窗口留白）

档位只表达「用户愿意在多大的上下文上花成本」，实际触发阈值再按模型窗口留白：

```text
threshold = min(选中档位, window - max(window × BufferPercent, MinBufferTokens))
            BufferPercent = 15（%），MinBufferTokens = 16000
            窗口小于两倍留白下限时，留白收敛为窗口的一半
```

- 1M 模型默认档 = 1,048,576 → 阈值 ≈ 891K（留白 15%）；用户手选 300K → 阈值 300,000。
- 128K 模型（`window < 300K`）→ 档位固定 128,000 → 阈值 ≈ 109K（留白 19.2K）。
- 档位只会让压缩**更早**发生，不会把阈值抬到窗口之上。

配置在宿主 `appsettings.json` 的 `LuBanAgent:Compaction` 段（`BufferPercent` / `MinBufferTokens` / `KeepTokens` / `SummarizePercent`），缺省即上表默认值；不改框架 `SessionOptions`，也不需要发包。

接口口径：`agent/sessionSettings` 返回的 `contextTier` 是**实际触发阈值**，可能落在档位清单之外（如 1M 窗口返回 891,290）。P2 做档位控件时，选中态应读会话存储的档位，不能直接拿这个值回填下拉。

> 风险提示（见 §10 第 4 条）：默认阈值贴近窗口 85%，单次请求更贵更慢；长会话首字延迟上升。冒烟重点看触发频率与成本，而不是「压缩后是否还超窗」。

### 7.6 主动压缩工具

`CompactContextToolPlugin`（`Tools/Context/CompactContextToolPlugin.cs`，注册于 `LuBanAgentExtensions.cs:65`）维持「显式压缩」语义不动；它按条数接收 `targetCount`，与本守卫正交，不互相覆盖。

### 7.7 已知边界

1. 预算未知的模型只靠超长兜底：必须先发一次必然失败的请求，才触发压缩。
2. 兜底只重跑一次；压缩后仍超长就报错，不做二次压缩。
3. 压缩失败不阻断对话（历史原样继续），但会发 `phase=failed` 让用户看到「未生效」。
4. 历史页仍展示已压缩消息（仅喂模型时按 `is_compacted` 过滤），用户可回看原文。
5. 归档窗口含 `system` 角色消息时，摘要器会把它单独前置保留，结果不再是「摘要 + 尾部」两条，本轮直接放弃压缩（不写摘要、不归档）。框架自身只落 `user` / `assistant` / `summary`，正常会话不会触发。
6. 压缩器解析失败（如未选择模型）时整轮跳过守卫、原样透传，不把内层本可转成 `ErrorEvent` 的起跑错误改成抛异常。
