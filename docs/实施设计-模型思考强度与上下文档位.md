# 实施设计：模型思考强度与上下文档位（Web 对话）

- 状态：设计已确认（4 项决策已定，见 §10），尚未落码
- 范围：`luban-agent`（Web 对话页 + 配置/会话存储 + 压缩策略）与 `luban-framework/LuBan.AIAgent`（压缩判定接缝）
- 上游设计依据：**无**。本文件是该需求的首份需求与实施设计，此前仓库内无相关 PRD。

---

## 1. 目标与非目标

### 1.1 目标

1. Web 对话页可按**当前模型**给出思考强度选项：模型不支持思考则不显示；模型只支持 2 档就只出现 2 项。
2. Web 对话页可按模型给出**上下文档位**（`300K / 600K / 900K / 1M` 这类），并在选中档位后**真实驱动会话压缩**，而不是只做个开关。
3. 思考强度与上下文档位支持**全局默认 + 会话覆盖**，与现有「全局默认模型 + 会话级模型」的选择模型一致。
4. 未登记的模型不猜测：默认只提供「跟随模型」，由用户在设置中心登记能力后启用。

### 1.2 非目标

- 不支持非标思考参数（`enable_thinking`、`thinking.budget_tokens`、`thinking.type`、`output_config.effort` 等）。本轮只走 `reasoning_effort` 的标准枚举子集。
- 不做模型能力的自动探测（不调厂商 models 端点推断档位）。
- 不改 CLI / Codex 的界面。二者继续不设值（跟随模型）。
- 不引入 token 精确计数（分词器）。仍用字符估算，见 §7.3。

### 3.2 由核查得出的三条硬结论

1. **厂商档位 ≠ 我们的枚举**。厂商普遍用 `xhigh` / `max` 作为最高档，而 `Microsoft.Extensions.AI` 只有 `None/Low/Medium/High/ExtraHigh` 五个值。映射已核实：`ExtraHigh` → `"xhigh"` 是通的；`minimal` 与 `max` 在本轮**发不出去**（详见 §3.4）。
2. **思考开关不统一，而且常常不在 `reasoning_effort` 里**。GLM-5.3 / Kimi K3 / MiniMax M3.1 明确**不允许关闭思考**；豆包 `doubao-seed-evolving` 与 GLM-5.2 的档位表里有 `none`/`minimal`（可停思考），但豆包「关思考」的官方推荐仍是 `thinking.type=disabled`（非标字段）；DeepSeek 关思考同样要 `thinking.type`。因此 `None` 这一项必须**按模型声明**，不能全局提供。
3. **没有厂商把"上下文长度"当请求参数**。绝大多数窗口是固定的，个别模型（qwen3.8-max）因思考模式不同，输入上限有几十 K 的差异。所以「上下文档位」只可能是**我们客户端的行为**（提前压缩），不可能是发给模型的参数——这一点在 §7 落地，UI 文案也必须照此表述。

### 3.4 标准链路能发出的值域（已核实）

`Microsoft.Extensions.AI.OpenAI` 11.0.0 的私有方法 `OpenAIChatClient.ToOpenAIChatReasoningEffortLevel` 是 `ReasoningEffort` 进 `reasoning_effort` 的唯一出口，其分支为：

```csharp
ReasoningEffort.None      => ChatReasoningEffortLevel.None,
ReasoningEffort.Low       => ChatReasoningEffortLevel.Low,
ReasoningEffort.Medium    => ChatReasoningEffortLevel.Medium,
ReasoningEffort.High      => ChatReasoningEffortLevel.High,
ReasoningEffort.ExtraHigh => new ChatReasoningEffortLevel("xhigh"),
_                         => null
```

校验方式：包内 `lib/**/Microsoft.Extensions.AI.OpenAI.dll` 的 UTF-16 字面量表里 `xhigh` 出现 1 次、`minimal` 出现 0 次；`OpenAI.dll` 2.14.0 的 `ResponseReasoningOptions` 值表里同时存在 `minimal`、`xhigh`、`max`。即：

| 我们可发的值 | 落到线上的 `reasoning_effort` |
|---|---|
| `None` | `none` |
| `Low` | `low` |
| `Medium` | `medium` |
| `High` | `high` |
| `ExtraHigh` | `xhigh` |
| （无对应值） | `minimal`、`max` **均不可发** |

1. 内置表只放「官方文档写明、且能映射到 §3.4 可发集合」的组合；`max` / `minimal` 一律不收（发不出去）。
2. 「无档位」用 `[]` 表达（含 `gpt-4.1`/`gpt-4o` 这类真·非推理模型，以及 `kimi-k2.6` 这类官方明确不支持参数的模型），UI 不出现档位控件。
3. 窗口值一律取官方「上下文长度」，不取「最大输入长度」（如 `qwen3.8-flash` 上下文 1,000,000，输入上限 991,808，取前者）。

## 4. 设计总览

### 4.1 三层数据

```
模型能力档案（是什么）              用户选择（要什么）          生效路径（做什么）
ModelProfiles[provider:model]  →  全局默认 / 会话覆盖  →  ① 每轮 ReasoningEffort
  内置表[模型 id]（兜底）                                   ② 压缩预算 = 档位值
  Reasoning: string[]?
  ContextWindow: int?
```

### 4.2 语义定义（关键，写死在文档里避免歧义）

| 字段 | `null` / 缺省 | 空数组 `[]` | 非空 |
|---|---|---|---|
| `Reasoning` | **未知**：UI 只给「跟随模型」 | **标准链路无档位**：不显示该控件（真·非推理模型，或官方明确不支持 `reasoning_effort`，或只能用非标字段开关） | 该模型可选的枚举名子集 |
| `ContextWindow` | **未知**：不显示控件，压缩沿用现有条数机制 | 同左（不允许 `0`） | 模型真实窗口 token 数 |

### 4.3 上下文档位派生规则（不落盘，纯计算）

依据用户规则：**低于 300K 的用模型最大长度；达到 300K 的按 300K 倍数分档，默认取 300K。**

```text
if (window == null)          tiers = []            // 未知
else if (window < 300_000)   tiers = [window]      // 固定，UI 只读展示
else {
    tiers = [300k, 600k, 900k, ...]                // k * 300k <= window
    if (window > tiers.Last()) tiers.Add(window)   // 末档取实际窗口
}
defaultTier = tiers.Count > 1 ? tiers[0] : tiers.FirstOrDefault()   // 300K
```

| 窗口 | 档位 | 默认 |
|---|---|---|
| 128K | `[128K]`（固定） | 128K |
| 300K | `[300K]`（等效固定） | 300K |
| 400K | `[300K, 400K]` | 300K |
| 600K | `[300K, 600K]` | 300K |
| 1M（1,048,576） | `[300K, 600K, 900K, 1M]` | 300K |

> 派生只依赖 `ContextWindow` 一个数，规则改了不需要迁移任何已存数据。

## 7. 压缩预算落地（唯一需要改框架的点）

### 7.1 现状为何不够

`SessionChatHistoryProvider.cs:106` 的判定是 `history.Count > _targetCount + _threshold`，`_targetCount` / `_threshold` 来自 `LuBanAgentOptions.Session`（`LuBanAgentOptions.cs:169`），装配在 `LuBanAgentFactory.BuildHistoryProvider`（`LuBanAgentFactory.cs:250`）。它**只看条数**，无法表达「1M 窗口」与「128K 窗口」的差别。

`IAgentSessionExtension`（`IAgentSessionExtension.cs`）只在**建 Agent 前**、会话 scope 上调用一次（`AgentHost.cs:448` 附近），拿不到每轮 history 的装配点，因此**不能**在产品侧直接改写判定维度。

### 7.2 新接缝（framework）

新增文件 `LuBan.AIAgent/Sessions/ISessionCompactionPolicy.cs`：

```csharp
/// <summary>会话历史压缩判定策略；未注册时框架使用按条数的默认实现（保持既有行为）。</summary>
public interface ISessionCompactionPolicy
{
    ValueTask<CompactionDecision> DecideAsync(CompactionContext context, CancellationToken ct = default);
}

public sealed record CompactionContext(
    string SessionId,
    IReadOnlyList<ChatMessage> History,   // 已构建、待发送的历史
    int TargetCount,                      // 来自 SessionOptions
    int Threshold);

public readonly record struct CompactionDecision(bool ShouldCompact, int TargetMessages);
```

- 默认实现 `CountBasedCompactionPolicy`：`ShouldCompact = History.Count > TargetCount + Threshold`，`TargetMessages = TargetCount` —— 与今天完全一致。
- `SessionChatHistoryProvider` 构造函数增**可选**参数 `ISessionCompactionPolicy? policy = null`（`:55`）；为 null 时用默认实现。这样框架内其他调用方零改动、行为不变。
- `:106` 的 `if` 改为读 `CompactionDecision`；`:111` 的 `new SummarizingChatReducer(_chatClient, _targetCount, _threshold)` 改为 `new SummarizingChatReducer(_chatClient, decision.TargetMessages, 0)`（策略已把「保留多少条」算好，阈值维度交给策略）。
- `LuBanAgentFactory.BuildHistoryProvider`（`:250`）从 scope 解析 `ISessionCompactionPolicy`（未注册则传 null）。

### 7.3 产品实现（`LubanAgentCore`）

`ModelBudgetCompactionPolicy`：

```text
budget = await settings.ResolveContextBudgetAsync(sessionId)
if (budget == null) → 回落到 CountBasedCompactionPolicy（今日行为）

total = Σ EstimateTokens(message)            // 估算方式见下
if (total <= budget) → ShouldCompact = false

// 从尾部往前累计，直到再加一条就超预算
keep = 0; acc = 0
for msg in History.Reverse():
    acc += EstimateTokens(msg); if (acc > budget) break; keep++
TargetMessages = max(2, keep)                // 至少保留最近一轮问答
ShouldCompact = true
```

token 估算沿用框架现有口径 `Math.Max(1, text.Length / 4)`（`SessionChatHistoryProvider.cs:394`），抽成 `ITokenEstimator` 以便后续替换。

### 7.4 预算取值（按用户定案）

**不设预算比例**：预算 = 选中档位值本身。

- 1M 模型选 300K → 预算 300,000。
- 128K 模型（`window < 300K`）→ 预算 = 128,000，用户不可调。

> 风险提示（见 §10 第 4 条）：预算按窗口值直接取，未给 system prompt、工具定义、输出 token 留余量。这是既定取舍，实施后需用冒烟观察 `ContextLengthExceeded` 是否变多，再决定是否调整（不在本轮擅自加系数）。

### 7.5 主动压缩工具

`CompactContextToolPlugin`（`Tools/Context/CompactContextToolPlugin.cs`，注册于 `LuBanAgentExtensions.cs:65`）维持「显式压缩」语义不动；它按条数接收 `targetCount`，与本策略正交，不互相覆盖。

## 10. 风险与未决

| # | 风险 | 影响 | 处理 |
|---|---|---|---|
| 1 | `minimal` / `max` 无法经标准链路发出 | GLM/Kimi/DeepSeek 的最高档（`max`）、OpenAI 系 `minimal` 在 UI 上缺失 | 设置页注明「该模型最高档暂不支持」；不假装支持 |
| 2 | `xhigh` 只在 OpenAI 官方口径核实，各厂商 Chat 端点是否接受未实测 | 登记 `ExtraHigh` 的模型可能 400 | §9.3 冒烟逐个抓包；失败就把该模型的 `ExtraHigh` 从档案里去掉 |
| 3 | 部分厂商对非法档位严格报错 | 用户手工登记错档位 → 请求 400 | 写入时按枚举校验；未知模型默认不发值 |
| 4 | 预算 = 窗口值，无余量 | 压缩后仍可能超窗 | 既定取舍；冒烟观察后再定 |
| 5 | `length/4` 对中文偏乐观 | 估算偏低 → 压缩滞后 | 记为已知偏差；后续可换分词估算 |
| 6 | 未知模型默认无控件 | 相比今天「能选 5 项」是能力收窄 | 内置表已覆盖 12 家 66 个模型 id（§3.5）；其余靠设置中心登记 |
| 7 | 内置表漏登会「明明支持却没有入口」 | 如 `glm-4.x`/`qwen3.7` 之下、混元/文心/盘古 | 已按 §3.3 单列未确认项；后续按需补 |
| 8 | 三端压缩行为同步变化 | CLI/Codex 也会按预算压缩 | 验收须带三端回归；已确认可接受 |
| 9 | framework 需发版 | 未发版时 P3 不可用 | 按用户节奏：先改码验证（`TEMP-LOCAL-VERIFY`），人工发包后再改回 `PackageReference` 并提交 |
